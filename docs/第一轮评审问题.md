## 一、 首轮评审识别的关键盲区与方案定案

### 1. 跨平台（特别是 Windows）进程生命周期与终端环境适配盲区
- **问题现状**：原设计基于 POSIX 规范的 `SIGTERM` / `SIGKILL` 信号打断。
- **现实踩坑点**：
  - Windows 原生不支持 POSIX 信号。在 Windows 下使用 `child_process.kill()` 仅杀死外层 shell（如 `cmd.exe` 或 `powershell.exe`），其衍生的子孙进程（如 `npm test`、`python server.py`、编译器进程）极易沦为**孤儿僵尸进程**，继续霸占端口、占用文件读写锁与内存；
  - 路径分隔符与 Shell 差异：Windows 下命令解释器可能有 cmd、PowerShell 5.1、PowerShell 7、Git Bash 等，不同环境对环境变量注入（`CI=true`）、管道链接符（`&&`、`;`）、通配符展开行为完全不同；
  - 控制字符与伪终端（PTY）：没有 PTY 支持时，许多 CLI 工具（如 Vite、Jest、Git）会进入无缓存或交互阻塞状态；
  - 换行符与编码差异：Windows CRLF 与 Linux LF 的混用，常导致代码精确定位替换（Edit Tool）报错 `oldString not found`，且控制台 GBK/UTF-8 编码不一致易产生乱码。
- **加固方案（吸收 OpenCode / pi 成熟经验）**：
  - 引入跨平台进程树硬杀机制（Windows 平台调用 `taskkill /pid <PID> /T /F`；Unix 平台调用 `kill -9 -<PGID>` 杀死进程组）；
  - 统一跨平台 Shell 探测与降级策略（Windows 优先探测 `pwsh.exe`，降级至 `powershell.exe` 或 `cmd.exe`）；
  - 针对文件替换增加换行符容错与模糊归一化处理。

### 2. 多模型厂商与思考模型（Reasoning / Thinking Tokens）协议治理
- **问题现状**：原设计基于传统 OpenAI 规范的 `tool_calls` 与 `content` 进行单轨上下文管理。
- **现实踩坑点**：
  - DeepSeek-R1、Claude 3.7 Sonnet、OpenAI o1/o3 等新一代推理模型，在流式响应中会输出独立的思考内容（如 `<think>` 标签或独立的 `reasoning_content` 字段）；
  - 推理 Token 体积庞大（单步可达数千至数万 Token）。如果将历史回合的所有思维链（CoT）毫无保留地全量带入后续回合，会以指数级速度爆掉上下文窗口并导致巨大的 API 资费浪费；
  - 但在单回合内部排查工具调用逻辑时，前端又必须能够实时查看思维链。
- **加固方案（参考 OpenCode 协议切分逻辑）**：
  - 事件表 `events` 显式增加 `reasoning` 增量事件类型，与正式文本 `content` 和 `tool_calls` 状态干净切分；
  - 数据库增加 `tokens_reasoning` 独立计量字段；
  - 在上下文状态机（`deriveMessages`）组装进入下一回合时，制定**思维链折叠/剥离策略**：历史回合默认剥离 `reasoning_content`，仅在持久化底层供人类审计查阅。

### 3. Git 状态冲突与原子回滚保障（开发者的“后悔药”）
- **问题现状**：原设计强调了写入前比对文件指纹防止覆盖外部手改，以及 commit 需审批。
- **现实踩坑点**：
  - 当 Agent 执行一个复杂任务，连续修改了 5 个文件，但在跑测试阶段发现方向完全错误且陷入反复调试死循环时，开发者需要一键回到本轮对话开始前的状态；
  - 如果人工手动一个个撤销改动，极易遗漏脏文件或新增的未跟踪文件（untracked files）。
- **加固方案（参考 OpenCode git.ts 封装）**：
  - 引入**回合级工作区 Checkpoint（检查点）机制**：在执行涉及物理修改的回合前，记录当前 Git 脏状态快照；
  - 在前端工作台提供【撤销本回合所有代码变更 (Revert Turn)】按钮，底层执行原子化的 `git checkout -- .` + `git clean -fd`，提供可靠试错兜底。

### 4. 网络代理体系（两级分流架构）与协议完善
- **核心定位与需求**：
  - 完美解决工程师环境“既要翻墙连外网 LLM，又要直连本地/局域网服务”的冲突矛盾。
- **加固方案（全面补全）**：
  1. **分类架构**：
     - **全局代理（系统级）**：在系统设置中心（`config-settings.html`）配置，控制系统全局外发流量；
     - **LLM 专项代理（Provider 级）**：在配置 Provider 端点信息模态弹窗（`config-providers.html`）中单独配置或继承；
  2. **端点卡片快捷开关**：
     - 在「已配置的 Provider 端点」选项卡列表中，每行/每张卡片配备独立的 **【是否开启代理】Toggle 开关**，支持不打开编辑弹窗即可秒级切换直连与代理；
  3. **完整配置要素**：
     - 代理协议：`HTTP` / `HTTPS` / `SOCKS5`；
     - 代理服务器地址（Host/IP）与端口（Port）；
     - 鉴权认证：用户名（非必填）、密码（非必填，密码框掩码）；
     - 绕过名单（Bypass / NO_PROXY）：默认注入 `localhost, 127.0.0.1, ::1, *.local`；
  4. **两级优先级流转**：
     - Provider 显式配置独立代理并开启 &rarr; 走 Provider 独立代理；
     - Provider 开启代理但选择“继承全局” &rarr; 走系统全局代理；
     - Provider 关闭代理 &rarr; **强制直连**（即便全局开启也不走代理，适配本地 Ollama 与国内大模型）。

### 5. Provider 接口类型与厂商协议扩展（OpenAI vs Anthropic 双轨制）
- **问题现状**：原设计仅泛化提到“OpenAI 兼容适配器”，未显式抽象接口协议类型。
- **现实痛点**：
  - 业界两大主流事实标准是 **OpenAI 规范**（`/v1/chat/completions`，标准 `tool_calls`）与 **Anthropic 规范**（`/v1/messages`，独有的 `thinking` 块、`cache_control` 提示词缓存与 `input_json` 工具调用契约）；
  - 纯靠 OpenAI 兼容层接入 Claude 无法发挥 Prompt Caching 与思考特性的威力。
- **加固方案**：
  - 在「新增/编辑 Provider 端点」界面中显式增加 **【接口协议类型 (API Protocol)】** 核心单选/下拉项：
    - 选项 A：`OpenAI Compatible`（默认，通用各聚合商、DeepSeek、Ollama 等）；
    - 选项 B：`Anthropic Native`（原生 Claude 消息协议，支持 Prompt Caching 与原生 Thinking）；
  - 列表卡片直观打上协议类型微章（`OpenAI` 或 `Anthropic`），底层调度器根据该标识自适应选用不同的请求 Payload 构造器与流式 Chunk 解析器。

## 二、 开源生态复用范围与边界定案

针对基于 OpenCode、pi 等成熟开源项目的可复用性讨论，正式确认以下**“分层复用与坚决隔离原则”**：

### 1. 严格限定的复用边界矩阵

| 系统层级 / 核心模块 | 复用策略 | 深度原因与明确边界 |
| :--- | :--- | :--- |
| **底层操作系统与执行适配**<br>（进程、Shell、文件、编码） | **重点吸收复用<br>（借鉴 OpenCode 与 pi）** | **核心收益最大**：两项目在 Win32 与 POSIX 平台的 Shell 探测（`pwsh` vs `powershell` vs `cmd`）、换行符（CRLF vs LF）比对替换容错、路径大小写规范化、非交互环境变量注入、ANSI 控制符剥离、进程树清理等底层细节上积累了极丰富的抗踩坑经验。这部分属于通用基础设施脏活，直接借鉴其成熟算法与逻辑，能够省去数月调试周期。 |
| **模型接入与 Provider 治理**<br>（模型配置、切换、流式传输） | **仅作协议参考<br>（坚决自研 Web 端体验）** | **OpenCode 体验存在硬伤**：OpenCode 的模型切换高度依赖 CLI 命令行或配置文件编辑，交互体验极不友好，且缺乏多 Provider 统一资产池可视化管理。<br>**自主路线**：我们保持既定的 Web 界面标准 Provider 资产池、运行时顶栏无缝秒切、一键请求 `/models` 自动探测拉取、双轨协议（OpenAI/Anthropic）、两级代理开关与独立压缩模型配置。仅参考其流式 Chunk 解析与 Reasoning 提取规范。 |
| **插件微内核与调度层**<br>（生命周期、扩展机制） | **坚决自研<br>（严禁参考二者）** | **架构设计理念冲突**：OpenCode 和 pi 均为纯 CLI 命令行或单线程简单循环。而我们采用 Cordis-like 的微内核（服务提供、注入、声明式依赖），并承载了**模式 A (流水线)、模式 B (子任务委派)、模式 C (BPMN 2.0 流程引擎)** 三大独特多智能体形态，必须自主掌控。 |
| **持久化与状态真相层**<br>（存储、事件日志） | **坚决自研<br>（严禁参考二者）** | **核心护城河与真相源差异**：二者均采用传统的内存消息数组（`Message[]`）或极简单的本地 JSON 文件；而我们以 **Node 22 原生内置 `node:sqlite`（WAL 模式）+ 追加式 `events` 事件表 + FTS5 全文倒排** 作为全系统唯一真相，这是支撑精确审计、断点恢复与回滚的核心，无法复用二者。 |

## 三、 架构盘问 (Grilling) 深度对齐与决策全量定案 (Q1–Q12)

经过逐项无遗漏盘问与双向确认，对极端场景、平台边界与系统流转的 12 项深层决策全量定案闭环：

| # | 核心分支领域 | 终局定案决策（权威事实） | 实现机制与参考来源 |
| :--- | :--- | :--- | :--- |
| **Q1** | **Git 回滚与手写冲突** | **轻量 Stash / Patch 快照隔离未提交代码** | 回合前检测若已有手写未提交修改，自动生成静默隔离快照。`Revert Turn` 时仅撤销本回合 Agent 产生的 Diff，坚决不冲掉用户原本的未提交手写代码。 |
| **Q2** | **Windows Shell 探测** | **`pwsh` &rarr; `powershell` &rarr; `cmd` 自动降级链** | 派生 PowerShell 时强制附加 `-NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass` 彻底绕过组策略权限限制，环境缺失或抛错自动降级至 cmd。 |
| **Q3** | **代理网络静默僵死** | **首包 30s + Chunk 静默 45s 硬超时熔断** | 杜绝代理网络下的假死等待。超时后优雅挂起为 `suspended`，通知人类排查代理或重试，**严禁静默降级为直连**以防敏感 IP 泄露。 |
| **Q4** | **Git 快照清理周期** | **单回合即时试错安全垫（最近 1 回合生命周期）** | Checkpoint 严格定位为当前回合的即时后悔药。新回合开启或用户显式发送新指令时，前一回合快照后台静默销毁，绝不污染用户的 Git Stash 列表。 |
| **Q5** | **多智能体写锁流转** | **父子租约让渡模型 (Parent-Child Lock Delegation)** | 子任务或流水线下游阶段继承父级写锁租约（`rootSessionId`）；子执行期间父挂起，子完成原路归还。彻底消解父子死锁，坚守工作区单写底线。 |
| **Q6** | **SQLite 双进程争抢** | **单实例文件锁防线 (`~/.harness/.lock`)** | 启动时校验锁文件中的 PID 与端口。若已有实例在跑立即安全阻断，提示现有端口或要求指定 `--data-dir`，根除 `SQLITE_BUSY` 冲突。 |
| **Q7** | **超长上下文滚动压缩** | **基于 Epoch/Seq 边界的无上限滚动压缩** | 彻底废除“限制压缩 2 次”的人工假定，完全参考 OpenCode `SessionCompaction`。以最新 `compaction.seq` 为历史切片起点，结合 `compactAfterOverflow` 自动从溢出中恢复。 |
| **Q8** | **`ask_user` 断线与唤醒** | **独立 `requestID` 寻址与回复/驳回双轨端点** | 参考 OpenCode `QuestionV2`。生成 `que_<uuid>`，暴露 `POST /api/questions/:id/reply`（回答）与 `/reject`（驳回）；重连时从事件表重新拉齐提问卡片。 |
| **Q9** | **MCP 工具重名防卫** | **强制命名空间前缀隔离 (`mcp__<server>__<tool>`)** | 外部 MCP 强制加前缀，本地 6 大编码工具（`read_file`, `edit_file`, `bash` 等）作为系统保留字独占，从协议根源防止本地沙箱被恶意/劣质 MCP 劫持。 |
| **Q10**| **多工作区记忆隔离** | **全局偏好与项目规约双层级联装配** | 参考 OpenCode `instruction-context.ts`。全局偏好存 `~/.harness/`，项目规约存 `<workspace>/.harness/`，请求前带明确来源前缀去重合并注入，避免技术栈污染。 |
| **Q11**| **Spill Blobs 清理** | **会话私有子目录物理隔离 (`~/.harness/sessions/<id>/blobs/`)** | 放弃复杂的全局引用计数。Spill 与会话生命周期绑定，删除会话时原子递归清空私有目录，无死锁、无误删、无孤儿文件。 |
| **Q12**| **SSE 息屏与休眠假死** | **服务端 15s 心跳 + 客户端 `visibilitychange` 自动重连** | 客户端 30s 无心跳或检测到屏幕点亮切回，立即主动掐断半开连接并携带 `?after=<seq>` 增量秒级拉齐，彻底消解浏览器后台节流假死。 |
